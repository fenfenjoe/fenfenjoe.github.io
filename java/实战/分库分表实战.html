分库分表实战

什么时候需要分库分表？

当单表数据量超过 1000万行 或单表数据文件超过 100GB 时，MySQL 的性能开始显著下降：

  • B+树层数增加（三层约 1000w），增加磁盘 I/O
  • DDL 操作（加字段、建索引）耗时指数级增长，可能锁表数小时
  • 单库磁盘 / IOPS / 连接数成为瓶颈
  • 备份和恢复时间过长

分库分表的核心思想：将数据分散到多个库/表，降低单节点压力，换取水平扩展能力。

不过不是所有千万级的表都需要拆。如果只是 append-only 的日志表、几乎没有查询，或者查询都在走时间区间小范围的索引，可以不加分表。

分库分表方式对比

方式示意图适用场景
垂直分表把一张宽表按列拆成多张表字段多（50+），冷热字段分离
垂直分库将不同业务表落到不同库微服务拆分，业务解耦
水平分表同一表的数据按规则分到 N 张表单表数据量过大
水平分库分表多个库 + 每个库多张表终极方案，写入/存储瓶颈

实际落地时，绝大多数场景用的是 水平分库分表——下面重点讲它。

ShardingSphere-JDBC 实战

一、引入依赖

<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-jdbc-core</artifactId>
    <version>5.5.0</version>
</dependency>

底层已包含数据源（HikariCP）、分布式主键等，无需额外引入。

二、数据分片规则

在决定怎么拆分前，先明确分片键（按哪个字段分片）和分片算法。

分片算法SQL示例优点缺点
MOD（取模）user_id % 4数据均匀分布扩容需大量迁移
HASH_MODhash(user_id) % 4比直接取模更均匀扩容同样麻烦
RANGE（范围）2025Q1 → ds0，2025Q2 → ds1扩容简单（新增库即可）容易产生热点
INTERVAL（时间分段）按月/按年路由天然支持冷热分离、归档写入集中在最新库
COMPLEX（复合）多字段联合路由灵活复杂度高

推荐：大数据量系统用 MOD / HASH_MOD + 预分片（初始化 N 个逻辑库，一开始映射到少量物理机，后续扩容只需搬迁部分）

三、application.yml 配置示例

以一个订单系统为例：order_id 作为分片键，分 2 个库 × 2 张表（一共 4 个分片）。

spring:
  shardingsphere:
    datasource:
      names: ds0,ds1
      ds0:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://192.168.1.10:3306/order_db0?serverTimezone=Asia/Shanghai
        username: root
        password: 123456
      ds1:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://192.168.1.11:3306/order_db1?serverTimezone=Asia/Shanghai
        username: root
        password: 123456

    rules:
      sharding:
        # 分库：order_id % 2 → 决定走 ds0 还是 ds1
        default-database-strategy:
          standard:
            sharding-column: order_id
            sharding-algorithm-name: database-inline
        tables:
          t_order:
            # 真实的物理表：t_order_0、t_order_1、t_order_2、t_order_3
            actual-data-nodes: ds$->{0..1}.t_order_$->{0..1}
            # 分表：order_id % 2 → 决定走 t_order_0 还是 t_order_1
            table-strategy:
              standard:
                sharding-column: order_id
                sharding-algorithm-name: table-inline
            # 分布式主键：雪花算法（内置）
            key-generate-strategy:
              column: order_id
              key-generator-name: snowflake

        sharding-algorithms:
          database-inline:
            type: INLINE
            props:
              algorithm-expression: ds$->{order_id % 2}
          table-inline:
            type: INLINE
            props:
              algorithm-expression: t_order_$->{order_id % 2}

        key-generators:
          snowflake:
            type: SNOWFLAKE

    props:
      sql-show: true  # 开发环境打印 SQL，方便排查路由是否正确

最终物理表结构：

数据源物理表
ds0（192.168.1.10:3306/order_db0）t_order_0, t_order_1
ds1（192.168.1.11:3306/order_db1）t_order_2, t_order_3
  • order_id % 2 = 0 → ds0 → 再 order_id % 2 = 0 → t_order_0
  • order_id % 2 = 1 → ds0 → 再 order_id % 2 = 1 → t_order_1
  • order_id % 2 = 0 → ds1 → t_order_2（但取模结果只能 0/1,所以 ds1 走的是 database % 2 = 1 的库内分表）

上面的 $->{0..1} 是 Groovy 表达式，actual-data-nodes 展开后就是 4 张表。

四、高级分片算法示例

上面用的是简单的 INLINE 表达式，适合规则固定的场景。生产环境常用自定义分片算法：

示例 1：基于时间范围的分片（按月）

tables:
  t_log:
    actual-data-nodes: ds0.t_log_$->{202501..202512}
    table-strategy:
      standard:
        sharding-column: create_time
        sharding-algorithm-name: log-month-range

sharding-algorithms:
  log-month-range:
    type: INTERVAL
    props:
      datetime-pattern: yyyy-MM-dd HH:mm:ss
      datetime-lower: 2025-01-01 00:00:00
      sharding-suffix-pattern: yyyyMM
      datetime-interval-amount: 1
      datetime-interval-unit: MONTHS

示例 2：一致性哈希（扩容友好）

sharding-algorithms:
  consistent-hash-mod:
    type: CONSISTENT_HASH
    props:
      sharding-count: "4" # 虚拟节点数量

一致性哈希在扩容时只需迁移约 1/N 的数据，而 MOD 几乎要全量迁移。

五、分片键选择建议

分片键选错了比不分表还惨。三个原则：

  1. 不可变 — 选业务生命周期内不会改的字段（用户ID、订单号），不要选 status、user_name
  2. 查询必有 — 绝大部分 SQL 的 WHERE 条件都包含这个字段，避免遍历所有分片（全路由）
  3. 离散度高 — 数据能均匀分散到各分片，避免热点。UUID / 雪花ID 天然离散；时间用月粒度、范围分片

常见反例： 按 status 分片 → 少量状态值导致数据倾斜 → 某些分片的热点无法消除。

六、全局 ID 生成

分库分表后，自增 ID 不可用（每个库自己从 1 开始），必须有全局唯一 ID。

方案原理优点缺点
Snowflake（雪花算法）（推荐）时间戳(41bit) + 机器ID(10bit) + 序列号(12bit)，吞吐量极高本地生成，不依赖DB，趋势递增强依赖时钟，时钟回拨需要处理
UUID32位16进制随机字符串绝对不重复非递增，B+树插入性能差，空间大
数据库号段模式从数据库批量取一段 ID 范围，用完再申请趋势递增，可定制依赖 DB，增加复杂度
Redis INCRRedis 原子递增趋势递增，实现简单依赖于 Redis

ShardingSphere 内置了 Snowflake，只需上面 key-generators 中配置即可。如果担心时钟回拨，可以：

  • NTP 校时不跳秒（tinker panic 0）
  • 使用美团的 Leaf-snowflake 方案（基于 ZK 的时钟同步）

七、强制路由（Hint 分片）

有些场景分片键不在 SQL 里，需要手动指定走哪个库/表：

// 强制路由到 ds0，不做 SQL 解析
try (HintManager hintManager = HintManager.getInstance()) {
    hintManager.setDatabaseShardingValue("ds0");
    hintManager.addTableShardingValue("t_order", "0");
    orderMapper.selectList(...);  // 强制走 ds0.t_order_0
}

适用场景：管理后台的全局统计、数据修复脚本等。

八、分布式事务

跨库写入需要分布式事务。ShardingSphere 支持两种模式：

模式原理适用场景
XA（默认推荐）基于 XA 规范的两阶段提交，依赖 Atomikos / Narayana强一致性要求，短事务
BASE（Seata）AT 模式，两阶段 + 全局锁长事务、高并发
rules:
  transaction:
    default-type: XA
    provider-type: Atomikos

九、读写分离 + 分库分表

在分片基础上叠加读写分离：

datasource:
  names: master0,master0-slave0,master1,master1-slave0

rules:
  readwrite-splitting:
    data-sources:
      ds0:
        write-data-source-name: master0
        read-data-source-names: master0-slave0
      ds1:
        write-data-source-name: master1
        read-data-source-names: master1-slave0

  sharding:
    tables:
      t_order:
        actual-data-nodes: ds$->{0..1}.t_order_$->{0..1}
        ...

# 最终效果：路由到 ds0 的写请求走 master0，读请求走 master0-slave0

十、分库分表后的常见问题

问题我的做法
跨分片 JOIN① 设计上避免关联——冗余字段、ER分片（把关联表放同一分片键）、全局表；② 必须 JOIN 时，代码层分别查然后拼装
跨分片分页① 流式 ID 分页：用 WHERE id > last_id LIMIT n 取全部分片汇总后排序截取；② 或用 ES 做全文检索，MySQL 只做单行详情
跨分片聚合COUNT / SUM 由 ShardingSphere 自动合并（对简单的 SELECT COUNT(*) 可直接改写），复杂的到业务层并行查询合并
扩容无损迁移停服 → 全量数据迁移 → 双写校验 → 切换路由规则 → 清理旧数据。不停服方案：使用增量同步方案（如 Cannel + Kafka）
分布式 ID 下的范围查询兼容Snowflake ID 是趋势递增但不连续，BETWEEN 范围查询仍有效（B+树叶子节点是按 ID 排序的）

ShardingSphere-JDBC 对大部分单表 CRUD 语法是透明的（INSERT / SELECT BY ID / UPDATE BY ID），应用代码几乎不需要改。

何时从 MySQL 切换到大数据平台？

MySQL 的极限在哪里？

MySQL（InnoDB）理论上可以支撑上亿行的表，但实际瓶颈在于：

维度瓶颈点表现
单表行数5000w ~ 1亿即使有索引，范围查询也变慢
数据文件大小200~500GB/单表ibd 文件过大，备份/DDL 困难
QPS 写入5000~15000/秒受限于锁竞争和磁盘 I/O
存储总容量几十 TB单库管理大量分片，运维压力大
分析性查询复杂 OLAP 查询大表 GROUP BY / 多表 JOIN / 全表扫描吃不消

核心判断标准：如果分库分表后，单表数据量仍在持续增长、或者业务出现了大量分析型需求（日报、BI 报表、用户画像计算），就该考虑引入大数据平台了。

触发切换的信号（满足任意一条）

  • 单表数据量 > 5000万 且持续增长，每月新增 1000万+
  • 需要做复杂的多维度 OLAP 分析（GROUP BY 非索引列、子查询嵌套）
  • 数据需要长期保留（半年以上），MySQL 存储成本高
  • 有实时/准实时数据处理需求（流式聚合、窗口计算）
  • MySQL 负责写入 + OLAP 分析，导致主库压力大、影响业务写入

怎么选大数据平台？

原则：MySQL 继续做在线事务（OLTP），大数据平台承接离线/实时分析（OLAP），两者通过数据同步管道打通。

场景推荐方案说明
BI 报表、离线分析Doris / StarRocks（推荐）SQL 兼容 MySQL，学习成本低；列存 + MPP 架构，分析查询秒级返回；可实时导入 + 支持物化视图
超大存储 + 批处理Hive + SparkHive 建在 HDFS 上，存储成本低（PB 级别），适合 T+1 批处理；查询慢（分钟级），不适合实时分析
实时流式处理Flink + Kafka实时 ETL、窗口聚合、CEP 规则；从 Kafka 消费 binlog → 清洗 → 写入 OLAP 引擎
搜索 / 全文检索Elasticsearch业务表数据同步到 ES，做全文搜索、模糊匹配、日志检索；不是分析引擎，不能替代 OLAP
统一数据湖（DLH）Hudi / Iceberg + Spark/Flink当数据源多、需要统一管理时，用湖仓一体方案（Hudi + Doris/StarRocks 查询层）

一个逐步演进的方案（实操参考）

阶段 1：ShardingSphere-JDBC 分库分表（1000w ~ 5000w）

  • 4~16 个分片足够应付 3~5 年增长
  • 所有 CRUD 继续走 MySQL，应用层透传

阶段 2：引入 OLAP 引擎（5000w+ 且出现分析需求）

  • MySQL 继续负责 OLTP（写入 + 点查）
  • Canal 把 MySQL binlog 写入 Kafka → Flink 清洗 → 写入 Doris/StarRocks
  • BI / 后台报表直接查 OLAP 引擎，不碰生产 MySQL
  • 数据归档：超过 N 天的历史数据可 DEPRECATE / 转移到 Hive（冷数据）

阶段 3：流批一体（上亿行且实时分析要求高）

  • Flink CDC 直接从 MySQL binlog 实时同步
  • Kafka + Flink 做实时 ETL，写入 Doris 实时表 + Hive 离线表
  • 复杂的标签计算、用户画像等离线跑批，Doris/StarRocks 做即席查询加速
┌──────────┐   binlog    ┌───────┐  real-time   ┌────────┐
│  MySQL   │ ─────────→ │ Canal │ ────────────→ │ Kafka  │
│ (OLTP)   │             └───────┘              └───┬────┘
└──────────┘                                         │
                                                  ┌──▼──────┐    ┌──────────────┐
                                                  │  Flink  │───→│ Doris / SR   │
                                                  └──┬──────┘    │ (OLAP 查询)  │
                                                     │           └──────────────┘
                                         离线(可选)  │
                                                  ┌──▼──────┐
                                                  │  Hive   │
                                                  │(冷数据) │
                                                  └─────────┘

一句话总结

  1. 千万级数据用 ShardingSphere-JDBC 水平拆分，4~16 个分片搞定未来几年的增长
  2. 当数据过了 5000 万且有复杂的分析需求，引入 OLAP 引擎（Doris/StarRocks）做读写分离——MySQL 负责业务写入，大数据平台做分析查询
  3. 选型建议：首选 StarRocks/Doris（兼容 MySQL 协议，迁移成本最低），有实时流处理需求搭配 Flink + Kafka
